## 1. Что такое ОСВЕД и зачем он создаётся

ОСВЕД (OSVED) — персональная русскоязычная **информационно-аналитическая система интересов и знаний**, а не просто RSS-агрегатор, не только Telegram-бот и не «чат в браузере».

Система:
- получает статьи, новости, видео, обсуждения, научные публикации, сообщения сообществ, релизы и сигналы;
- связывает их с первоисточниками, событиями, компаниями, людьми, авторами, продуктами и технологиями;
- дедуплицирует повторения, отличает сигнал от доказанного факта;
- переводит по запросу или согласно установленной политике, делает короткие и глубокие русские выжимки;
- формирует персональную ленту, дайджесты, наблюдения, исследования и библиотеку;
- объясняет рекомендации, учится на явной обратной связи без скрытого «наказания» источников;
- предоставляет единый веб-кабинет, Telegram-бот и Telegram Mini App с одной базой и общей логикой;
- в перспективе позволяет пользователю управлять выбором AI-провайдеров, моделей и цепочек обработки вплоть до отдельного канала.

Основной замысел владельца: **информационный поток подстраивается под человека**, помогает видеть важное в IT, AI, разработке, инфраструктуре, бизнесе и новых направлениях, не заставляет читать сотни повторов. Важна не количественная лента, а качественный отбор, глубина и способность находить неожиданно полезные связи.

Пользователь предлагает идеи в ходе работы, часто неформально и «на ходу». Их нужно собирать, сопоставлять с действующими возможностями и разумно внедрять, не требуя постоянного микроменеджмента.

## 4. Источники: полное видение, актуальная функциональность и недостатки

**Желаемый сценарий:** пользователь вставляет обычную ссылку из браузера, например GitHub repo URL, r/Python, YouTube/@name, t.me/channel, X/@author, Habr author/feed, блог, RSS. Сайт распознаёт платформу и тип, проверяет формат, показывает название/автора/категории, даёт сохранить или добавить в тематическую подборку. Для сервисов с закрытыми API показывает честную доступность и альтернативу.

Должны поддерживаться:
- добавление **одной** обычной ссылки на канал, сообщество, репозиторий, автора, публикацию или RSS;
- **пакетный импорт** ссылок из вставленного списка и TXT/CSV; предпросмотр, галочки, категории, проверка дублей, отчёт;
- управление активностью, интервалом сбора, квотами, тематикой, приоритетом/доверием и конкретными авторами;
- предложения похожих авторов, компаний, каналов и тематических площадок; рекомендация источника отдельно от рекомендации публикации;
- синхронизация собственных подписок при разрешённом подключении личного аккаунта;
- единая база и одинаковые настройки сайта/Telegram.

### Уже реализовано в main по последней проверке

- Каталог источников разделяет платформы: Telegram/мессенджеры; X/соцсети; Reddit/V2EX/сообщества; YouTube/видео; GitHub/разработка; RSS/сайты; Weibo/Zhihu и другие.
- Фильтрация по платформе и присвоенной теме, статус/пауза, ссылка на оригинал, время последнего успешного сбора при наличии.
- **GitHub:** пользователь добавляет публичный owner/repo или обычный GitHub URL; используется existing collector для релизов.
- **Reddit:** пользователь добавляет публичный r/community или URL, темы, пауза/удаление; источник попадает в существующий коллектор.
- **YouTube:** публичный channel/UC ID; введён удобный @handle/канальный URL с **явным подтверждением возможного платного Monid-запроса**. Не считать handle бесплатно доступным при отсутствии бесплатного официального resolver. Коллектор проверяет публичный Atom-feed.
- **Пакетный импорт**: список/TXT/CSV (первый столбец), до **25 ссылок**, локальный предпросмотр, выбор строк, стандартные GitHub/Reddit/прямые YouTube channel-ID. Unsupported показываются без попытки сбора. Действительный массовый импорт — последовательные вызовы существующего backend, не отдельный второй коллектор.
- Источники и пользовательские подключения сохраняются в SQLite; скрытое удаление не стирает историю.
- Важно: эти функции проверялись API/unit и Chromium UI, но **никакой CI сам по себе не доказывает, что все внешние платформы реально и регулярно отдают контент**.

### Следующие улучшения

1. Объединить разрозненные формы добавления в один понятный мастер «Добавить источник», определяющий платформу по обычной ссылке. Поддерживать URL, ник, канал, сообщество, блог, repo.
2. Единая модель: platform / source / channel_or_author / source_topic / article_topics / account_connection / status / health / quota / last_success.
3. RSS/Atom на любых безопасных доменах с защитой SSRF: проверка DNS/IP, private/reserved IP запрет, повторное подтверждение после каждого редиректа, лимит размера/таймаут/кеш/частота. Сначала фиксированный allowlist известных сайтов, если безопаснее.
4. Поддержка Telegram public channels, X public authors и других платформ только согласно легальным/действующим API и без обхода ограничений. Русскоязычные площадки через их разрешённые публичные RSS/API.
5. Предложить популярные каналы/авторов/компании с объяснением «почему рекомендовано», выбором приоритета источника и отпиской.
6. Пакетный CSV формата platform,url,category,topics,mode,priority и серверная валидация/отчёт. Ограничение и dry-run перед импортом.
7. Контент одного канала может относиться к **разным темам**; классификация канала не означает, что вся статья автоматически относится только к той же категории.

## 5. Личные аккаунты и синхронизация подписок

**Пожелание владельца:** подключать в «Настройки → Аккаунты» свои YouTube, X, Reddit, Telegram, GitHub и другие аккаунты. После разрешённой авторизации система получает список **доступных через API личных подписок**, показывает предварительный список, даёт выбрать интересные каналы/сообщества/авторов и импортировать их в «Источники». Периодическая синхронизация с журналом и кнопкой «Отключить/удалить доступ». Сайт должен ощущаться функционально, как удобные настройки подписок в исходном приложении, но без нарушения приватности.

План по провайдерам:
- **YouTube / Google:** официальный OAuth, read-only доступ к собственным подпискам, постраничная загрузка, выбранные каналы; отдельно работа с публичными видео/субтитрами.
- **GitHub:** официальный OAuth или GitHub App с минимально нужным scope для stars, following и доступных watches; не путать «звёзды» и «отслеживаю релизы».
- **Reddit:** собственные сообщества по допустимому read-only OAuth при доступном API/тарифе; иначе импорт собственного списка.
- **X:** официальный разрешённый API с реальными правами и тарифами. Если персональные подписки недоступны, объяснить честно и дать импорт вручную, не обходить платные ограничения.
- **Telegram:** переиспользовать имеющийся MTProto/Telegram-reader при правомерной доступности; **не** просить session-string, пароль, экспорт браузерных cookie. Отдельное разрешение/сессия, хранение, защита и отзыв доступа.
- Для остальных аккаунтов применить те же правила: user consent, OAuth state/PKCE, read-only scope, шифрование токенов, expiry/refresh, revoke/delete, audit, rate limits.

**Фактический статус:** личные OAuth-аккаунты перечисленных сервисов НЕ подключены в current main. Публичный канал по URL — не личная синхронизация. Не ставить фиктивные кнопки «Аккаунт подключён» или автозагрузку приватных подписок без согласия.

## 6. Персональная лента, состояние чтения и обратная связь

### Четыре разных действия — не смешивать

| Действие | Поведение | Влияние на персонализацию |
|---|---|---|
| **Скрыть / ✕ / Закрыть** | Убрать эту карточку, не открывая и не читая; вернуть из «Скрытые» | **НЕТ**, даже если скрыто много карточек |
| **Прочитано** | Отметка чтения, заметка в библиотеке | НЕТ без явно выбранной оценки |
| **В избранное / Читать позже** | Сохранение для доступа позднее | НЕТ автоматически |
| **Больше такого / Меньше такого / Не моё** | Явная оценка содержания, модели и похожих тем | ДА, на явно выбранном уровне |

Дополнительные сигналы: «Уже знаю», «Поверхностно», «Нужен глубокий разбор», «Следить за темой/автором», «Рекомендация ошибочная», «Всё равно показать важное». «Показать меньше статей именно этого канала» — **отдельная** настройка уровня source, не то же самое, что «меньше про эту тему».

**Фактически:** app/web/personalization.py использует прозрачные эвристики классификации по заголовку/краткому описанию, ручные веса тем от -3 до +3 и обратную связь для ранжирования. **Это не обученная AI-модель**, не полноценное понимание глубокого контекста статьи, не автоматическое понижение конкретного автора/канала. Признак «почему показано» есть, но объяснения пока простые. Нейтральное скрытие с восстановлением уже реализовано в свежем main; отдельная таблица app/web/hidden_items.py, API /api/hidden.

### Развитие алгоритма

- **Стабильные крупные категории:** AI/программирование, инфраструктура/сети, кибербезопасность, бизнес/стартапы, наука/исследования, дизайн/творчество, другие (точные существующие ключи сверить с app/web/folders.py).
- **Собственные темы внутри категории:** AI-агенты, GPU, cloud, информационная безопасность, системная архитектура, строительные технологии и т. п.; система предлагает тему, пользователь подтверждает или правит.
- **Объекты интересов:** компании, люди, авторы, продукты, технологии, репозитории, бренды; подписки/запреты управляются независимо от источника.
- **Контекст статьи:** не только принадлежность канала категории; оценивать утверждения, смысл, новизну, качество источника, глубину, язык, практическую ценность. Не сохранять секретные интересы/профили во внешние AI без разрешения.
- Пользователь может сам вручную менять уровень приоритета, стоп-темы, частоту, полноту текста. Явные правила всегда сильнее автодогадок; история объяснима и сбрасывается.
- **Главное для меня**; **Слежу**; **Радар**; **Открытия** (необычные новые темы); **Исследования**; **Не пропустить важное**; **Библиотека**; **Тихий режим и дайджест**.
- Оценка «меньше подобного» не должна автоматически скрывать все новости компании или канала, пока пользователь сам не выбрал scope=source/company/author.
- Сохранить разнообразие и источники вне информационного пузыря, защититься от кликбейта, дублей и низкокачественной генерации.
- Нормализация источников, ссылка на оригинал, история события, степень верификации и «почему рекомендовано» — разные независимые поля.

**Жизненный цикл материала:** новое / в ленте / прочитано / сохранено / скрыто / отложено / архивировано. Скрытое не удалять из поискового индекса и истории без отдельного требования; восстановление должно работать после обновления сайта. Обсудить автоматическую чистку видимой ленты без удаления исходных данных.

## 7. КРИТИЧЕСКОЕ НОВОЕ ТЗ — интеллектуальное управление AI-моделями в кабинете

Это отдельная **явная заявка владельца**, поступившая при передаче handoff. **Добавить полноценный раздел «AI-модели и обработка» на сайте**, интегрированный с Telegram, общей БД и текущими provider clients. **Ниже целевая спецификация, НЕ реализованная текущей веб-версией.**

### 7.1. Концепция

Одна платформа, множество источников, разные модели, полностью настраиваемая обработка информации. Пользователь самостоятельно выбирает **какого провайдера и какую модель для какой задачи и для какого источника** использовать. Не ограничиваться глобальным переключателем.

### 7.2. Центр AI-управления: функции

- Выбор основного AI-провайдера (по умолчанию **Codex Sale**, если работает), конкретной реальной модели и подтверждённого статуса API.
- Модели отдельно для задач, источников, каналов, отдельных сценариев.
- Общий язык, приоритет **русского**, auto-translation, терминология, стиль, глубина обработки и формат результата.
- Собственные инструкции для типов задач/источников; версии шаблонов и предпросмотр.
- Модель по умолчанию; явно включаемая резервная модель/провайдер, поведение при 402/429/timeout.
- История операций, стоимость, использованные токены (если достоверно доступны), кеш-хиты, ошибки и статусы.
- Настройки и изменения из UI, без ручного редактирования конфигов; ключи — **только на защищённом backend**, не передаются браузеру.
- Кнопка тестового прогона по **одной** выбранной статье, сравнение результата и оценки расхода до сохранения профиля.

### 7.3. Задачи и профили обработки

| Задача | Результат |
|---|---|
| Новости | Короткая выжимка, главные факты, контекст события |
| Статьи | Структурированный пересказ, идеи, выводы, оригинал |
| Исследования | Глубокий анализ, сопоставление данных, ссылки |
| Перевод | Русский/другой язык без изменения смысла, чисел и терминологии |
| Аналитика | Тренды, закономерности, связи и осторожные прогнозы |
| Мониторинг | Значимые изменения, новые события, версии, упоминания |
| Дайджесты | Тематические обзоры без дублей |
| Проверка фактов | Сравнение утверждений с первоисточниками, честные неопределённости |
| Поиск/классификация | Источники, сущности, типы публикаций, рубрики |
| Видео/субтитры | Краткий разбор YouTube, глубокое исследование, PDF |
| Изображения | Обложка, инфографика, карта знаний — по отдельной цене/задаче |

Готовые режимы: **«Экономный»**, **«Сбалансированный»**, **«Глубокий анализ»**. Далее расширенный режим параметров и «Собственный AI-профиль».

### 7.4. Правила для отдельных источников

В карточке каждого источника — вкладка/панель **«AI-обработка»**:
- общие настройки или собственный профиль;
- модель для перевода/пересказа/проверки/извлечения фактов;
- автоматический или ручной запуск;
- кратко/полностью/только факты/глубокое исследование;
- язык, частота и расписание;
- лимит операций, токенов и стоимости на один канал;
- правила при недоступности модели и ограничения на передачу приватного текста.

Примеры: **Hacker News** — перевод на русский и краткий пересказ; **Habr** — исходный русский текст без лишнего перевода; **научные публикации** — глубокий анализ с источниками; **YouTube** — русская выжимка из субтитров выбранной моделью.

### 7.5. AI-конвейеры / цепочки

Простой:
**Источник → Сбор → Нормализация → Перевод (при необходимости) → Выжимка → Классификация → Сохранение в ленту.**

Сложный:
**Несколько источников → Дедупликация и кластеризация → Сопоставление фактов → Исследование → Аналитический отчёт → Контроль качества → Доставка.**

На разных стадиях разрешены разные модели; сбор сырья независим от генерации. При смене модели переработать можно **сохранённый** исходник, не выполнять повторное внешнее подключение. Артефакты кешируются по hash(content + model + instructions + locale + version), оригинал/ссылки остаются.

### 7.6. Одна логика на сайт и Telegram

- Вся конфигурация хранится централизованно в SQLite/runtime settings или развиваемом **одном** реестре моделей, с версионированием.
- Telegram — быстрый выбор задач/моделей и просмотр статуса; сайт — полная расширенная консоль. Любая смена настройки в одном интерфейсе отражается в другом.
- Роль и scope выбранной модели проверяются и в API, и в обработчике задач. **Не создавать два несовместимых каталога**.
- Отказ модели → понятная причина, проверяемая альтернатива, явное разрешение на потенциально платный fallback. Не переключаться тихо на более дорогую модель.
- Стабильные ID моделей получать из **реального** Codex Sale /models с текущего аккаунта; не придумывать названия и коэффициенты.

### 7.7. Codex Sale: не забыть существующую заготовку

В открытом **PR #1** уже есть:
- app/llm/codexsale.py — клиент OpenAI-совместимого API Codex Sale и /models;
- app/llm/model_registry.py — модель по задачам и runtime setting keys;
- изменения app/llm/openrouter.py и нескольких обработчиков;
- Telegram кнопочное меню и выбор моделей по задачам в app/telegram_bot/model_menu.py.

**Это WIP, не main, не доказанная работоспособность на Hermes.** Нельзя переносить ветку целиком: в ней кроме provider кода есть широкие изменения в CLI/планировщиках, source handling и Telegram. Выделить отдельный актуальный PR от свежего main, покрыть тестами текущие процессы и подключить веб.

**OpenRouter** оставить резервным вариантом только при явном разрешении; его отсутствие в current main не равно «невозможно использовать AI вообще». Статус и диагностику провайдера исправить на приоритет Codex Sale после реального подключения. До фактической настройки не писать «AI готово».

### 7.8. Экономика и безопасность

- По умолчанию бесплатный сбор, локальная нормализация, дедупликация и кеш.
- Недорогая модель для перевода/тем/кратких текстов; сильная для глубокого анализа только по запросу. Не предполагать, что внутренние тарифные коэффициенты — долларовая стоимость.
- Лимиты бюджета на операцию/день/месяц, safe hard-stop, резерв перед внешним платным вызовом, журнал провайдера/модели/токенов/расхода; защита от двойной оплаты при uncertain results.
- Не отправлять секретные материалы во внешние модели без согласия; не считать AI-вывод фактом без первоисточников.
- Наличие модели в каталоге не доказывает поддержку нужного endpoint, embeddings, изображений или аудио — подтверждать реальным безопасным probe.

## 8. YouTube, перевод статей и медиалаб

**Видеосценарий:** вставка обычного YouTube URL → проверка доступности/прав на субтитры → извлечение/кеш транскрипта или разрешённой расшифровки → **краткая выжимка** и **развёрнутый смысловой разбор** на русском с таймкодами, контекстом и оригинальными ссылками → экспорт в PDF/заметки/материалы.

Пользователь хочет вставлять URL без терминальных команд и разбираться, что происходит, через понятные кнопки. Учитывать отсутствие субтитров, языки, таймкоды, квоты и неполные ролики, не выдумывать факты из одного заголовка.

**Фактически на момент среза:** UI ввода URL существует, старая видеоцепочка ориентирована на Monid + OpenRouter. OpenRouter не настроен на Hermes по последней диагностике, а целевой Codex Sale пока в draft PR. Проверенной новой платной выжимки на боевом сервере не было. **Не писать, что YouTube summary работает, только потому что форма есть.** Мониторинг и импорт подписок YouTube — отдельная задача.

**Перевод статей:** по кнопке «Перевести на русский»; кратко или полный доступный текст; оригинал/русский рядом; кеш перевода; указание модели, даты и «машинный перевод»; корректность имён, цифр, формул, ссылок. Автоматизация переводов по профилю источника — после подключения бюджетного движка.

**Медиалаб и генерация:** короткий пост, подробное исследование, структурированный документ/PDF, цитаты из видео в пределах авторских прав, тезисы для собственного ролика, карта фактов. Фотореалистичная генерация изображений — отдельный backend/provider, а не SVG с притворным ярлыком AI. Сейчас есть генерация SVG-обложек; опционально AI-изображения для обложек, схем, иллюстраций и инфографики с явной маркировкой, 목적ью, правами и квотами.

- Модель данных единая и миграция/rollback разумны; пользовательские исходники не теряются.
- Авторизация владельца, CSRF, безопасный URL/scope, rate limits, квоты, no secret leakage.
- Python/unit и UI/browser тесты; **реальный** внешний провайдер/сборщик проверяется отдельно, тесты с моками не подменяют его.
- PR/CI/pass → merge → auto-deploy по exact SHA → health → внешний smoke.
- Отдельный budget/usage log для платных операций и подтверждение до расхода.
- Правильные русские тексты и состояния, светлая/тёмная тема, мобильная/десктопная проверка.
- Короткое обновление handoff/roadmap, что реально сделано, что осталось.

## 12. Как новому разработчику продолжить без уточняющих вопросов

1. Прочитай перечисленные документы и проверь живой main/PR/CI/сервер.
2. Воспринимай этот handoff как **приоритет пользователя**, но при расхождении выбирай более свежий код и живые логи. Особенно учти, что майн уже содержит скрытие, bulk import и YouTube handles. **Не начинай с повторного внедрения этих функций.**
3. Отдели старый незавершённый Codex Sale PR #1 от текущего main; проверь актуальные /models и совместимость, план провайдера и бюджетов.
4. Доведи минимум одну реальную карточку и русскую выжимку; синхронизация настроек AI-сценариев на сайт/бот должна использовать единый backend.
5. Дальше постепенно расширяй источники, подключение собственных аккаунтов, темы, рекомендации и медиалаб. Приоритеты и безопасность важнее «всё за один PR».
6. Никогда не спрашивай владельца повторно о том, что в документах уже решено. Спрашивай только о недостающих реальных OAuth-app credentials, consent либо о денежном лимите, если это действительно блокирует операцию. Не проси отправлять ключи в чат.

**Завершающая продуктовая формула:**  
**ОСВЕД = источники + разрешённые личные подписки + проверка информации + русский контент + управляемые AI-модели + прозрачные рекомендации + персональная память знаний.**

**Ключевое новое пожелание:** всё это должно управляться **из сайта**, а Telegram служить быстрым и синхронизированным интерфейсом. Codex Sale — основной целевой провайдер. Система должна минимизировать расходы и показывать реальное состояние каждого этапа.
